# 主动照护建议：后端接入说明

本轮以“了解老人—提出有依据的尝试—人工安排—执行反馈—主管复核”为主线，增加生活照护建议闭环。接口前缀为 `/api/v1`，只增加后端能力，前端尚未联调；新增合同供前端协作确认。原有记录、任务、印象、记忆和交接班接口保留。

## 1. 用户会获得什么

例如，张阿姨的正式记录写着“本人说喜欢午后听戏，音量小一些”。系统可建议“先询问本次是否愿意，愿意时播放小音量戏曲”，同时给出原文、来源版本和不确定性。护理员核对当前意愿并填写负责人、班次、期限及完成标准后，建议才会成为普通任务。

完成或未执行后，护理员登记本人的反应和实际观察，系统保存为正式记录，供下次整理老人印象时使用。主管可选择继续尝试、调整、停止或证据不足。一次接受或拒绝均不会自动改写长期偏好，不会训练模型或更新模型权重。

## 2. 权限与状态

- 所有接口使用现有登录令牌。护理员限当前照护范围，主管和管理员按机构范围操作；家属无权读取此内部工作资料。
- 建议状态：`proposed`（待选择）、`adopted`（已采纳）、`rejected`（暂不采用）。采纳状态仅表示已人工安排，不表示已执行或有效。
- 人工操作均带 `expected_revision`，发生版本冲突时返回409，刷新核对后再提交。
- 采纳、拒绝、反馈、复核均支持 `Idempotency-Key`。同一次请求重试保留原键；同键不同内容返回409。未传键时仍以状态/版本阻止重复采纳、重复有效反馈。
- 时间均带时区。模型不能填写真实人员编号、正式期限或确认状态。

## 3. 整理建议

`POST /elders/{elder_id}/care-advice/generate`

```json
{"scene":"activity","shift_id":"DAY","lookback_days":30}
```

`scene` 可选 `bathing/dining/activity/communication/rest/other`；`shift_id` 可不传；回顾窗口1～90天，默认30天。

上下文只包含当前权限内、当前入住的正式记录，及场景相关的有效记忆、已审批有效计划和当前可见待办。正式记录取窗口内最近30条，按发生时间（无则录入时间）选择，排除未来、旧入住和未确认记录。记录尚未分类场景，需模型及工作人员判断相关性，不能声称全部记录已按场景精准筛选。任务和计划只是安排，不能视为服务已发生的证明。

返回 `batch_id,coverage,model_status,provider,model,prompt_version,items,notice`。`coverage.recent_records` 说明窗口内符合条件、实际纳入、因数量限制排除的条数。上下文过大返回422，不截断原文中的否定或前提。

每条建议包含：

| 字段 | 含义 |
|---|---|
| `title/action` | 建议标题与可尝试动作 |
| `rationale/uncertainty` | 为什么建议、有哪些不足或待核实点 |
| `condition` | 执行前须核实的前提，无则null |
| `citations/evidence_sources` | 逐字引文与当时来源版本快照 |
| `source_current/source_issues` | 依据现在是否仍有效、变化原因 |
| `expired/can_adopt` | 是否过期、当前是否可采纳 |
| `revision/status/task_id` | 版本、选择状态、关联正式任务 |
| `feedback/reviews/latest_review/needs_review` | 执行反馈、复核历史与待复核提示 |

至少一处引用来自正式记录或有效记忆；仅有计划、待办不足以支持个性化建议。不存在的来源、拼造引文、重复引用或非法结构均拒绝，不保存建议。文字规则过滤部分明显诊断、用药内容；该过滤不能保证所有语义绝对正确，仍须人工核对。

模型调用在JSON写锁之外，保存前重新检查权限、老人状态及上下文。同账号、角色、上下文、模型和提示版本相同的批次在24小时内复用，避免反复生成重复建议。并发请求仍可能产生多次供应商调用，但只保存一个相同批次。切换模型、提示版本或上下文后生成新批次。

无正式依据返回422；模型超时、非法输出或引用错误返回503。模拟模式明确返回 `model_status=demo, items=[]`，不伪造个性化建议；真实模型也可以返回空数组。

## 4. 查看与选择

- `GET /elders/{elder_id}/care-advice`：按 `scene,status,limit,offset` 筛选，返回 `total,items,notice`；默认50条、最多100条。
- `GET /elders/{elder_id}/care-advice/{advice_id}`：建议详情，包括原文快照、关联任务、反馈与复核。
- `POST .../{advice_id}/reject`：提交 `expected_revision,reason`，说明本次不采用的原因；不把拒绝当作偏好失效。
- `POST .../{advice_id}/adopt`：提交以下结构：

```json
{
  "expected_revision":1,
  "reason":"已与本人核对，本次愿意尝试",
  "task":{
    "elder_id":"E1",
    "title":"询问本人意愿后安排小音量戏曲",
    "source_type":"manual",
    "shift_id":"DAY",
    "assigned_to":"staff",
    "due_at":"2026-10-26T15:00:00+08:00",
    "completion_criteria":"记录本人是否愿意和当次感受",
    "condition":null
  }
}
```

示例日期、编号仅示意，前端必须选择真实班次、人员和未来期限。护理员只能安排给自己，主管可按已有班次规则分配。建议前提必须保留到任务；不能删除条件绕过核验。任务创建和建议状态在同一个JSON事务中提交，任何校验或落盘失败均不留半成品。

任务新增只读字段 `source_advice_id`，用于回到建议依据。继续使用既有开始、完成、未执行、转交、取消、交班、条件核验接口。依据变化阻止开始或完成；采纳后经过24小时不会仅因建议生成期限到期而使既有任务自动失效。

## 5. 登记实际执行反馈

先用既有任务接口登记 `completed` 或 `not_done`，再调用：

`POST /elders/{elder_id}/care-advice/{advice_id}/feedback`

```json
{
  "expected_revision":2,
  "expected_task_revision":2,
  "response":"accepted",
  "observation":"本人愿意听戏，并表示当前音量合适。",
  "happened_at":"2026-10-26T14:30:00+08:00",
  "shift_id":"DAY",
  "followup":"none"
}
```

- `response`：`accepted/declined/unclear/not_obtained`，只表示本次意愿或反应，不是疗效或模型准确率。
- `observation`：人工核实的当次情况；`happened_at` 不早于任务创建且不晚于当前时间。
- `followup`：`none/observe/supervisor_review`；非none时还须填写 `followup_assigned_to,followup_due_at`，按既有任务规则生成“复核本次照护反馈”待办。该字段是跟进意图，不自动授予主管权限，也不自动指定主管。
- 反馈、正式记录、可选跟进任务在同一事务保存。反馈引用任务当时版本、结果和记录版本，后续更正仍保留原快照。
- 同任务版本已有有效反馈时拒绝再次保存；旧反馈记录更正后允许重新登记一份反馈，旧反馈保留并标为来源非当前。主管复核以最新反馈为依据，保留全部历史。

## 6. 主管复核

`POST /elders/{elder_id}/care-advice/{advice_id}/review`

提交 `expected_revision,expected_feedback_fingerprint,decision,note`。指纹直接使用最新详情返回的值，它同时覆盖反馈及当前引用来源，防止打开页面之后的来源更正被误当成已核对。

| decision | 含义与效果 |
|---|---|
| `continue_trial` | 本次复核后可继续尝试；依据已变化时不允许选择 |
| `adjust` | 需要重新安排；阻止关联任务再次开始/完成，保留原任务历史 |
| `stop` | 停止本次尝试；阻止关联任务再次开始/完成，不自动取消历史任务 |
| `insufficient_evidence` | 记录证据不足，不能声称已证实有效；不自动改变任务或长期记忆 |

没有反馈、任务/反馈版本已变化、最新反馈已更正时不能直接复核。应先核实并登记当前反馈。复核不是诊断，也不自动更新照护计划或长期记忆；确需调整时使用原有人工审核流程。

## 7. 变更、通知和追溯

- 来源更正的影响预览新增 `kind=care_advice`，并列出其关联任务及交班；反馈记录更正也会定位到所属建议。只追踪明确引用，不猜测语义关系。
- 首次反馈后通知主管待复核；复核完成后关闭通知。来源或反馈随后变化，查询通知时重新检查并补入一次提醒；没有后台定时推送，前端需要刷新或轮询。
- 老人时间线纳入建议生成、采纳、拒绝、反馈、复核；建议详情时间线可关联来源记录、执行任务和反馈记录。护理员撤权后不能继续查看内部建议历史。
- AI治理增加 `care_advice` 类型及提示版本、模型标识和请求耗时记录；人工可对合成/脱敏留出集提交误提、漏提、引用错误评估。调用成功率与人工采纳均不等于建议正确率。

## 8. 前端最小接入方式

不必增加独立“AI工具”菜单。在老人详情或当前服务页增加“照护建议”内联区：选择场景→整理→查看依据与不确定性→采纳/暂不采用。采纳弹出已有任务表单；任务结果下方接“本次反馈”；主管待办接复核。

界面显示中文标签，不展示内部枚举、版本编号或长ID作为标题。提交按钮区分等待、完成、失败和待核实；失败时保留输入。后台生成期间不阻塞日常记录保存。旧页面未经接入不会自动出现本轮能力。

## 9. 存储与上线

JSON schema 7 新增 `care_advice,care_advice_batches` 集合。延续文件锁、原子替换，不引入数据库。旧schema 1～6启动前必须先停服、备份并显式运行现有迁移脚本；迁移本身先保存原文件备份，不重置账号或旧业务。回退旧代码时需匹配schema的备份，不能直接让旧代码读取schema 7。

本轮尚未推送、部署或执行线上迁移。建议先由前端确认合同和接入，再按测试流程联调。真实模型的建议质量需另行验收，不能引用普通回归的通过率作为模型准确率。

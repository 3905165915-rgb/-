# 事务存储迁移与恢复方案

## 当前代码与部署依据

当前源码使用 `JsonStore`，`CURRENT_SCHEMA_VERSION` 为 **10**。业务集合存放在 `store.json`，照片文件存放在同一数据目录下的 `attachments/`。写操作持有 `FileLock`，完成整份数据的读取、校验和业务修改，再把临时文件经 `fsync`、`os.replace` 替换为正式文件。集合之间的业务修改、审计和幂等记录在同一次 `mutate` 中提交。

部署模板指定一个 Uvicorn worker，后台整理线程也在应用进程内启动。当前源码和依赖未使用 SQLAlchemy、Alembic 或事务数据库。文件锁和原子替换保证当前写入方式的完整性，但整份文件读写、内存过滤和单机附件目录限制了扩展方式。增加 worker 或复制应用实例前，需要先完成存储和后台作业协调改造。

以上是仓库事实。线上进程数、实际数据目录、文件系统、备份计划及恢复记录需由运维提供证据；公网健康接口只能说明该接口当时的响应，不能证明这些部署条件成立。仓库中的历史发布说明不代替本次核对。

本轮取得的证据：2026-11-03 公开只读访问 [`/api/v1/health`](https://sdau.fun/api/v1/health) 返回 HTTP 200，内容为 `status: ok`、`environment: demo`、`schema_version: 10`。该响应不包含源码提交、进程数、存储路径或备份记录。本地存储、备份和照片恢复相关17项测试通过；这些结果未覆盖事务数据库导入和线上恢复。

源码依据：[`json_store.py`](../app/storage/json_store.py)、[`workflow.py`](../app/services/workflow.py)、[`attachment_service.py`](../app/services/attachment_service.py)、[`main.py`](../app/main.py)、[服务模板](hulaozhijiao.service)、[依赖清单](../requirements.txt)。

## 迁移目标与不变项

目标方案采用 PostgreSQL 承接业务事务，照片保留在受控文件存储或对象存储中。数据库适配器、数据导入器、数据库迁移文件和作业协调机制需另行实现、评审和验收；本文不代表它们已经完成。

首轮迁移保持接口和业务语义，保留全部集合、顶层扩展字段和对象内容。可以先保存完整的结构化对象，再增加查询列和索引；不得因新表暂未覆盖某个字段而丢弃该字段。以下内容逐项对照原快照：

| 内容 | 保留要求 |
| --- | --- |
| 对象与引用 | 原字符串 ID、老人及入住关联、任务来源、交班关联、所有版本号和历史快照保持不变；不得重新编号。 |
| 审计 | `audit_logs` 的 ID、事件顺序、操作人、时间、对象及扩展明细完整保留；迁移记录另记，不改写历史事件。 |
| 幂等 | 保留用户、操作、键、请求指纹、原响应及创建时间；数据库对用户、操作、键建立唯一约束，业务结果和幂等响应同事务提交。 |
| 账号与授权 | 保留账号 ID、密码散列、会话版本、家属授权、照护分配和自动化授权的原状态；迁移不重置账号或扩大授权。 |
| 时间与状态 | 保留原时间文本、时区、发生时间与登记时间的区别，以及终态、撤销和待审核状态。 |
| 附件 | 保留 ID、`storage_key`、字节数、`sha256`、`original_sha256`、审核历史及引用关系；逐文件校验已存照片的 `sha256`。原始上传文件未保存时，不把 `original_sha256` 当作可重新核验的文件。 |
| 待处理作业 | 保留作业 ID、来源版本、状态、领取信息和失败记录；切换期间停止领取，恢复执行前核对来源与已完成结果。 |

当前所有 `mutate` 调用需按业务操作梳理事务边界。例如，正式记录、审计、通知投影和整理作业不能分别提交；任务创建与幂等响应不能分离。已有 `expected_revision`、来源版本及上下文检查继续保留，并转为事务内条件检查。外部模型调用仍在数据库事务外执行，保存结果时重新核对资料版本。

数据库事务无法同时提交照片文件。上传需先写入并核验不可变文件，再在事务中写入引用；失败后的孤立文件由有留存期和引用核对的流程处理。迁移阶段不自动清理原文件。后台作业需具有持久领取、超时恢复及重复执行去重机制，验收前继续维持单 worker。

## 先完成离线演练

1. 运维确认发布负责人、数据库负责人、业务确认人、停机窗口和回滚决策人。根据演练测得的备份、导入与恢复耗时约定恢复时限和可接受数据损失范围，记录确认结果。
2. 在受控隔离环境使用经授权的副本演练；开发回归使用合成数据。生产副本按真实业务资料管理，不上传公开仓库，不在日志或报告中输出正文、照片和凭据。
3. 生成源快照清单：源码提交、schema、快照时间、文件摘要、集合计数、对象 ID 集摘要、规范化对象摘要、引用核对结果、附件清单及逐文件摘要。对未知字段也生成摘要。
4. 新建独立数据库并运行已评审的建表与导入程序。导入应可重复核验；任何重复 ID、冲突幂等键或无法解析的关联都形成阻断清单，由业务确认后处理，不能静默覆盖或跳过。
5. 从数据库导出规范化快照，与源清单逐集合、逐对象比较。仅允许事先列明的存储表达差异，例如数据库时间列的规范化；原始值仍需保留以便追溯。
6. 用正常业务流程核对读写响应、版本冲突提示、原提交重试、跨对象事务和后台作业恢复；确认一个操作的业务结果、审计及幂等记录共同提交。校验附件链接与文件摘要。保留结果和未通过项。
7. 在隔离环境完整演练切换前回退，以及切换后新增数据的导出、对账和回收流程，记录实际耗时。未解决的差异不带入正式切换。

### 现有离线清单工具

[`storage_manifest.py`](../scripts/storage_manifest.py) 读取指定的当前 schema 离线快照，校验集合结构及被引用照片的 SHA-256，生成整份 JSON 摘要、各列表集合的计数与规范化内容摘要、照片 ID、摘要和字节数。它不初始化、恢复或改写源数据；输出必须是独立的新文件，输出目录须提前备妥。文件变化会中止核验，仍需先取得已经停写的快照。

从仓库根目录执行的示例，路径均指向隔离备份副本和受控证据目录：

```sh
python backend/scripts/storage_manifest.py /secure/backup/store-snapshot.json \
  --attachments /secure/backup/store-snapshot.attachments \
  --output /secure/evidence/pre-migration-manifest.json
```

省略 `--attachments` 时，工具读取源 JSON 同级的 `attachments/`；成套备份的照片位于 `.attachments` 目录，需像示例一样显式指定。当前工具验证 schema 10，不直接迁移旧快照。它提供文件与集合层面的核对，逐对象差异、关联完整性和数据库导出对账仍由后续迁移工具完成。

## 正式停机与备份

| 顺序 | 操作与完成条件 |
| --- | --- |
| 1. 进入维护 | 暂停新业务请求、上传和导入，等待在途请求结束，停止应用及会写入的后台进程。确认进程和作业已经停止；页面显示维护状态不能代替停写确认。 |
| 2. 锁定基线 | 记录最终停写时间、源码、依赖及配置文件的受控备份位置。配置原值只保留在授权备份中，验收报告只记位置、权限及摘要。 |
| 3. 备份数据 | 使用当前备份工具保留 `store.json` 及其配套 `.attachments` 目录，并保存原数据目录的受控快照。二者作为一个备份集登记，不只复制 JSON。 |
| 4. 核对备份 | 确认 JSON 可解析、schema 与目标兼容，集合和 ID 清单匹配，每个被引用照片存在且摘要一致。记录备份集摘要、访问权限和异地副本位置。 |
| 5. 备份恢复确认 | 在隔离目录验证备份可读、照片完整及恢复流程可执行。检查既有备份任务的最近结果、失败告警和留存策略；未取得运维证据的项目标为待核对。 |

既有 `backup_json.py --restore` 是业务恢复工具：它会保留当前账号、递增会话版本、清空旧幂等响应与通知，并撤销部分授权、分配和作业状态。因此不能把它当作逐字段保留的迁移导入器或无损回滚器。备份原件只读保管，演练使用副本。

## 导入、核验与开放顺序

正式导入使用最终停写快照，记录迁移批次 ID 和来源摘要。目标数据库在导入及核验完成前不接收业务流量；数据库提交失败时保留原快照，并重新创建隔离目标进行排查，不修改源数据。附件先复制并逐一校验，数据库引用只指向已经核验的文件。

开放前需同时满足以下条件：

- schema、集合计数、对象 ID、完整内容摘要、引用、审计和幂等记录核对通过，差异清单为空或有逐项批准的转换说明。
- 全部被引用附件存在，文件字节摘要与记录一致；原存储和回滚备份仍可用。
- 新适配器的正常业务回归通过，关键跨对象提交和原提交重试结果正确；没有测试结果的容量及恢复时间不写成已验证指标。
- 数据库备份已配置并完成恢复演练；运维确认实际应用进程、连接目标、文件目录及监控状态。
- 回滚所需的旧代码、原快照、附件、配置及差异回收工具齐备，决策人与停机窗口仍有效。

先启动维护模式下的单 worker 服务，后台领取保持暂停，核对健康响应、数据读取和后台配置。业务确认人核对关键页面与对象后，再开放写入；记录第一笔新事务的时间及迁移批次。按已验收的恢复规则逐步启用后台作业，核对未完成作业，避免重复触发模型调用或重复生成业务对象。

## 回滚路径

**尚未开放写入时**：停止新服务，确认目标数据库没有迁移以外的新业务写入；切回匹配原快照的旧代码、配置和原附件目录。比较原 JSON 与停写基线摘要后再启动单 worker。原快照未改写时无须调用会改变授权和幂等状态的业务恢复工具。记录回滚原因、目标数据库留存位置和核对结果。

**已经开放写入后**：先重新进入维护状态，停止所有写入和作业；备份目标数据库、附件及当前旧存储，保留从开放时刻起的全部业务、审计、幂等和作业变更。使用经过演练的反向导出或差异回收程序，把这些变化完整纳入兼容旧代码的数据集，重新核对 ID、版本、关联、摘要和重复提交结果。核对通过后才能切换回旧存储。

直接把停机前的 JSON 覆盖回去会丢失开放后的业务。差异回收未实现或核对不通过时，保持维护并修复数据库服务，由负责人决定恢复路径；不能通过重建演示数据、重新编号或清空幂等记录掩盖差异。若恢复动作涉及会话或授权失效，需记录具体变化并通知业务重新核实。

## 交接记录

交接包包括：源码和依赖标识、停写与开放时间、运维部署证据、源快照清单、附件摘要、备份与恢复记录、数据库迁移文件、导入导出结果、差异处理批准、业务核对结果、回滚演练记录及负责人签认。报告只呈现核对结论和受控证据位置。

本方案尚未执行停机、导入、恢复或数据库切换。本轮核对限于公开健康响应、仓库代码和上述本地结果，未登录服务器；线上存储状态与实际恢复能力仍需相应运维证据和演练结果。

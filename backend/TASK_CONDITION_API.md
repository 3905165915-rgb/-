# 条件待办核验（0.3.5，2026-10-20）

本功能落实清单第5项：任务有“等家属回复后”“若本人仍有此意愿”等条件时，明确谁核验、依据是什么、核验有效到什么时候、跨班后谁继续负责。仅处理已写入 `task.condition` 的条件，不保证从任意自然语言完整识别所有限制，也不执行医疗判断或自动照护。

## 完整链路与边界

1. AI提取或人手建立候选任务，正式确认后保存原条件文本；此时尚未核验。
2. 主管明确可操作的核验标准、指定有效工作人员，可设提醒期限。
3. 指定核验人引用同一老人的当前正式记录，明确选择“满足”或“未满足”，填写说明；满足时必须填写有效截止时间。
4. 条件满足且仍有效时，原执行人/主管才可按已有任务权限开始或完成任务；条件核验本身不执行任务。
5. 条件未满足、来源被更正、核验到期或核验人不可用时，阻止开始/完成。仍可记录未执行、转交、恢复待办或由主管取消，避免无法登记真实进展。
6. 跨班沿用原任务，保存上班核验快照与历史，清空当前核验人和结论；接班人员明确认领后重新核对。旧交班内容不覆盖。

“回复已入记录”不等于核验满足；“核验满足”也不等于已完成服务。本版没有家属身份核验、家属电子签字、消息收取、自动催办或事件触发器；家属回复由工作人员依法取得并如实录入正式记录，再由指定人核对。

## 接口和权限

路径前缀 `/api/v1`，工作人员JWT。家属无权访问。原有任务接口路径不变，新增：

| 方法 | 路径 | 权限/作用 |
|---|---|---|
| GET | `/tasks/{id}/condition` | 工作人员查看原始核验历史和当前有效性，读取不写入 |
| POST | `/tasks/{id}/condition/configure` | 主管/管理员明确标准并指定核验人；重新配置会撤销当前结论，保留历史 |
| POST | `/tasks/{id}/condition/claim` | 跨班后，按现有任务执行权限明确认领尚未指派的核验责任；不能抢占已有核验人或自行配置标准 |
| POST | `/tasks/{id}/condition/check` | 仅当前指定核验人可提交结果；主管也不能冒用他人的核验身份 |

全部新写接口需 `expected_task_revision`，并支持 `Idempotency-Key`。同key同内容返回原响应快照；相同key换内容409。任务转交或核验人重新指派后，旧人员不能用重试绕过当前权限。最新情况必须重新GET。

所有写入在JSON文件锁事务内复查账号、当前角色、任务版本、班次开放与当前成员权限。核验人若是护理员，须属于当前任务班次；管理人员可被指定为核验人。任务执行者与核验人可以不同，两者权限分别校验。

## 状态说明

`verification.status` 是最后存储的人工状态，不能作为实时执行许可。动态状态位于专用GET的 `current`：

| current.state | 含义 | 可开始/完成 |
|---|---|---|
| `not_required` | 无条件文本且无核验配置 | 仍受原任务/班次权限约束 |
| `unconfigured` | 有条件文本，尚未由主管配置 | 否 |
| `awaiting_assignment` | 已有标准，跨班后需认领核验责任 | 否 |
| `waiting` | 已明确核验人，尚未提交本次结论 | 否 |
| `not_met` | 人工确认当前未满足 | 否 |
| `met` | 人工确认满足、引用仍有效、未到有效期 | 仍受原任务/班次权限约束 |
| `needs_recheck` | 证据变更、有效期届满或核验人不可用 | 否，须重新核验 |

`current.ready` 表示条件是否允许继续，`current.execution_allowed` 还检查任务是否为可执行状态及班次是否开放，但不替代具体操作者权限。`historical_only=true` 表示已完成/取消任务，不再接受新核验；历史可保留过期提示，不自动重开。

`check_due_at` 是提醒期限，届满仅显示 `overdue` 并可被规则质检发现，不会自动变为“已满足”。`valid_until` 是人工结论有效期，届满含等于当前时刻即失效。它们都要求带时区。核验人被停用、变为非工作人员或不再属于任务班次时，需主管重新指定；旧签署记录不删除。

## 请求示例

以下ID从实际接口取得，时间应换成未来时间。

主管配置：

```json
{
  "expected_task_revision":1,
  "criterion":"核实家属对本次活动安排的回复，记录原话及时间",
  "checker_id":"USER-...",
  "check_due_at":"2026-10-21T10:00:00+08:00",
  "reason":"明确本次活动的核验标准和责任人"
}
```

`check_due_at` 可省略/null；传值须晚于当前时间。`criterion` 是人工补充的操作标准，不覆盖原始 `task.condition`；本版没有删除条件或跳过核验的接口。重新配置会重置当前核验结论，即使任务已开始，也须重新核验后才能完成。

指定人员提交：

```json
{
  "expected_task_revision":2,
  "outcome":"met",
  "note":"已核对本次活动回复，按本人当前意愿安排",
  "valid_until":"2026-10-21T12:00:00+08:00",
  "evidence":[{
    "record_id":"REC-...",
    "revision":1,
    "field":"observations",
    "quote":"家属回复同意本次活动安排"
  }]
}
```

`outcome` 只接受 `met/not_met`，不由模型或规则代填。`met` 必填 `valid_until`；`not_met` 可省略有效期，有填写也须是未来时间。未满足可再次核验，历次结论均保留。

`evidence` 必填1—5项：同一老人、当前正式记录版本、逐字引用；字段只接受 `observations/raw_text`。已更正记录不能再引旧raw_text作为当前依据。服务端保存当时原文快照，客户端不能传入快照或自行填写核验人/核验时间。记录之后被更正时旧结论失效，但快照保留。

引文存在不证明回复人身份、行为实际发生或结论语义正确，必须由人核对。例如本人的当前拒绝不能因“家属之前同意”而被忽略；本版不做这种语义裁决。

跨班后认领：

```json
{
  "expected_task_revision":4,
  "reason":"接班后认领核验责任，继续核对本次安排"
}
```

`claim` 只改变当前核验责任，不复用上班结论。新核验人需再次提交 `check`。可重新核对仍适用的原记录，也可引用新记录；不能把“重新检查原记录”当作“家属再次回复”。标准未配置时须先由主管配置。

## 读取、原任务接口与错误

专用GET响应含 `task_id/task_revision/task_status/condition/verification/current/historical_only/as_of`。`verification` 保存标准、核验人、期限、最新人工结论和不可覆盖的历次变更历史；`current` 另给状态、可用核验人、证据是否当前、期限及拦截原因。

普通任务GET/列表新增可选 `condition_verification`，只表示存储快照，缺少该字段的旧数据按null读取，不补造确认。前端需要实时状态时调用专用GET；不要用原始 `verification.status == met` 允许按钮。后端无论前端如何显示，都会在原 `start/complete` 写入时重新检查条件。

常见业务错误：

| 状态码 | detail | 含义 |
|---|---|---|
| 403 | `only_condition_checker_can_check` | 当前用户不是指定核验人 |
| 403 | `task_assigned_to_another_caregiver` | 无权认领其他人负责的任务条件 |
| 403 | `staff_permissions_changed` / `not_a_shift_member` | 当前账号/班次权限不足 |
| 409 | `task_condition_not_ready` | 条件尚未满足当前执行要求，不能开始/完成 |
| 409 | `condition_requires_configuration` | 需要主管先明确标准 |
| 409 | `condition_checker_already_assigned` | 已有核验人，需主管重新指派 |
| 409 | `stale_revision` / `shift_closed` / `task_is_terminal` | 资料变化、班次关闭或任务已结束 |
| 409 | `condition_evidence_not_current` | 引用版本不是当前正式记录 |
| 422 | `task_has_no_condition` | 无原始条件文本，不能凭空配置 |
| 422 | `condition_checker_not_in_shift` | 核验护理员不属于当前任务班次 |
| 422 | `condition_evidence_elder_mismatch` / `condition_evidence_quote_not_found` | 串人或伪造引用 |

不合法时区、缺少满足结论有效期、伪造字段等返回FastAPI 422 detail数组。前端需兼容业务错误码与参数校验数组；409应保留输入并请人核对当前资料，不能自动替用户确认。

## 交班、AI和质检的连锁反应

- 配置、认领、核验都会增加原任务版本；旧交班草稿要刷新后再提交。
- 交班条目保存 `condition_verification` 历史快照及 `condition_check` 当时状态。即使任务版本未变，来源更正或自然到期造成当前条件状态变化，也会要求刷新草稿；AI摘要生成期间发生变化会拒绝保存。
- 接班仍沿用原任务ID与记忆采用关系，条件核验责任另行清空；历史通过 `carry_task_condition` 留痕。已提交交班快照不变。
- 上下文AI仅取得条件文本及当前核验元数据，不注入旧核验证据全文。来源更正/到期会改变上下文，旧AI草稿不能直接确认。
- 提示词禁止模型自行认定条件已满足、自动触发或完成任务；普通AI候选/手工task_candidates不能注入 `condition_verification/condition_check`。
- 规则质检增加 `task_condition_blocked` 和 `condition_check_overdue`；仅提示人工处理，不改任务或核验状态。AI质检等待期间条件状态变化也会使扫描失效。
- 任务时间线可查看配置、核验、认领、跨班失效、核验证据的更正事件；引文与操作人、时间均保留。

## 前端交接与交付范围

管理端：任务详情增加标准、核验人和提醒期限配置；工作台可结合规则质检发现未核验/超期事项。护理端：展示条件状态、当前核验人和证据，提供认领与人工核验表单；开始/完成受状态限制。家属端尚无这些业务接口。

当前仅提供后端接口交接稿，供前端协作者确认；没有修改前端页面或执行服务器部署。JSON schema仍为4，没有新增集合或必填存储字段；已有v4无需迁移，旧v1/v2/v3仍须按原说明显式迁移。单服务器JSON只适合小规模演示，仍待联调、Linux运行验收、真实语义评测与机构试用。

# 变更影响队列与人工核验（0.3.3）

本接口把“任务采用的记忆已经变化”接成可追踪的核验流程。仅支持已有任务采用关系的影响核验；不包含尚未实现的照护计划变更、不良事件整改或医疗责任认定。使用单机构、单服务器JSON，未引入数据库。

## 检测与链路

正式记录更正 → 相关记忆转待复核 → 已采用该记忆的未结束任务出现差异 → 自动建立核验单 → 主管指派 → 负责人按原业务接口处理 → 引用正式记录提交结果 → 另一位主管复查并关闭/退回。

- 记忆修订、请求复核、停用等已有写入动作，在同一文件锁事务中检查影响并建单。核验入队失败则整个写入不提交。
- 自然到期、外部导入或历史积压由主管主动执行 `POST /change-reviews/scan` 补查。本版没有后台定时扫描、短信/推送或实时通知；需要前端在工作台提供扫描入口。
- 同一任务、同一采用关系仅有一张未关闭核验单。重复扫描不重复建单；检测到新差异时追加观察并更新版本，初次证据不覆盖。新的差异需要再核验时，待复查状态退回已指派，已有提交保留。
- 新核验单不自动指派、不自动执行任务、不自动关闭。完成/取消任务、已撤回采用关系不会新建核验单；已有单仍需处理并复查，不能自动消失。
- 读取接口只读取当前状态，不写入、不扫描建单。列表中的 `needs_review` 与核验单状态独立：处理已经解决差异时，核验单仍须复查。

## 接口和权限

路径前缀 `/api/v1`，使用工作人员JWT。所有写接口支持 `Idempotency-Key`；相同键、相同操作者及同内容重试返回原响应快照，当前情况应重新GET。

| 方法 | 路径 | 权限/作用 |
|---|---|---|
| POST | `/change-reviews/scan` | 主管/管理员补查，可按老人过滤 |
| GET | `/change-reviews` | 主管看全部；护理员仅看指派给自己的单 |
| GET | `/change-reviews/{id}` | 与列表相同；返回当前差异及提交所需版本指纹 |
| POST | `/change-reviews/{id}/assign` | 主管指派/重新指派有效工作人员和可选期限 |
| POST | `/change-reviews/{id}/submit` | 仅当前负责人提交处理结果，主管不能代替他人直接提交 |
| POST | `/change-reviews/{id}/review` | 主管复查；通过时必须与提交人不同 |

家属不能访问。护理员通过老人/任务等时间线也不能绕过核验单的指派限制。核验单指派只授予该单的处理权限，不授予原任务的执行权限、其他班次交班单的读取权限或全部老人访问权。需要原任务负责人/主管按已有权限先处理原任务。

列表支持 `status`、`elder_id`、`task_id`、`assigned_to`；`limit` 默认100、最大200，`offset`默认0。未知状态返回422。

## 状态机与请求

`pending → assigned → awaiting_review → closed`；复查退回到 `assigned`。重新指派也回到 `assigned`，保留提交和复查历史。关闭后不能再编辑，也不会重开任务。

扫描请求：

```json
{"elder_id":"E1"}
```

传 `{}` 扫描全部现有任务，响应包括 `as_of`、`scanned_tasks`、`created_ids` 和 `updated_ids`。没有未完成任务的历史差异不会被补造成待处理事件。

其余写接口都需要从最新GET复制 `revision`、`fingerprint`，分别填写 `expected_revision`、`expected_fingerprint`。指纹为64位SHA256；覆盖任务版本/负责人/班次、当前采用关系与替代依据、相关交班条目及版本，不包含读取时刻。版本或资料发生变化返回409，重新GET后由人核对，禁止前端静默重试覆盖。

指派请求字段：

```json
{
  "expected_revision":1,
  "expected_fingerprint":"从GET复制64位fingerprint",
  "assigned_to":"staff",
  "due_at":"2026-10-20T10:00:00+08:00",
  "reason":"请与本人核对活动安排并处理旧依据"
}
```

示例指纹是说明占位，实际请求必须替换；示例期限也须替换为未来时间。`due_at` 可省略或为null；传值须有时区且晚于当前时间。读取动态给 `overdue`，不会将逾期自动等同失职。

处理步骤：先按现有任务接口撤回旧引用、明确采用有效新引用，或由有权限的人结束任务；再重新GET核验单，提交结果。提交不会代为执行这些动作。

```json
{
  "expected_revision":2,
  "expected_fingerprint":"从GET复制64位fingerprint",
  "disposition":"reference_withdrawn",
  "note":"已向本人重新核对并撤回旧采用依据",
  "evidence":[{
    "record_id":"REC-...",
    "revision":2,
    "field":"observations",
    "quote":"本人表示改为下午活动"
  }],
  "acknowledged_handover_ids":["HO-..."]
}
```

处理结论与后端约束：

| disposition | 真实状态要求 |
|---|---|
| `reference_withdrawn` | 原采用关系已撤回 |
| `reference_replaced` | 原关系已撤回，且任务存在相同场景、当前有效且无差异的新采用关系 |
| `task_terminal` | 任务已完成或取消；仅核验历史，不重新打开任务 |
| `no_current_difference` | 原关系仍有效采用，当前版本、来源、场景及期限检查均无差异 |

任务或原采用关系缺失/串人、关联交班父单缺失时阻止提交，不静默忽略数据问题。旧引用仍需核验时不能仅凭备注提交“已解决”。新依据由处理人明确选择，系统不能判断其语义是否足以替代原依据。

`evidence` 必填1—5项，限同一老人的当前正式记录，含记录版本和逐字引用；字段只接受 `observations` 或 `raw_text`。已更正记录不能再引旧raw_text作当前依据；服务端保存引用所在原文的快照，客户端不能提交快照。引用存在和流程状态符合不能证明服务实际发生、照护决策正确或引文语义支持结论，仍须人工复查。

复查请求：

```json
{
  "expected_revision":3,
  "expected_fingerprint":"从GET复制64位fingerprint",
  "decision":"accept",
  "note":"已核对当前依据、本人记录和交班关联，复查通过"
}
```

`decision`为 `accept` 或 `return`。通过须由另一人执行，资料指纹仍与提交时一致，引用仍是当前版本和原文，处理结论仍满足。仅重新GET不能使旧提交自动变成有效；资料改变后要退回、重新核验并提交。退回会保留原提交、意见、复查人及当时上下文。

## 交班与审计

- `initial_snapshot` 固定保存初次发现的采用内容/来源/任务版本/交班定位；`observations` 记录后来检测到的差异，`submissions` 和 `reviews` 保留每次人工处理。
- `current.handovers` 列出包含该任务的交班条目，含交班ID、条目ID、源/目标班次、版本、状态、是否保存该引用以及采用版本。即使交班草稿早于采用关系建立，也会定位该任务。
- 对已提交/接收交班，`historical_only=true`；处理人必须在 `acknowledged_handover_ids` 明确列出所有这些交班ID，避免漏看。此确认仅表示处理人声明已核对关联，不证明已通知所有班次人员。
- 已提交交班内容、旧采用快照不会被队列覆盖。交班草稿仍通过原 `refresh` 刷新；刷新、接班或任务转交改变当前上下文后，旧处理提交会被拒绝，需重新核对。
- `/items/{case_id}/timeline` 及相关任务/老人/记忆的时间线可查看入队、再次变化、指派、提交和复查事件。指派/提交/复查含操作人、时间和请求内容；不会为关闭核验自动生成服务完成记录。

## 前端接入顺序

1. 管理工作台提供扫描和状态筛选；展示“资料已解决但待复查”与“当前仍有差异”。
2. 核验详情并列展示初次快照、当前状态、相关交班、历次提交和复查意见。
3. 主管指派；护理员消息/工作台通过列表查询自己的核验单。本版没有消息推送服务。
4. 原任务页按现有权限处理引用，返回后重新GET核验单；选择真实处理结论、正式记录引用及交班核对项再提交。
5. 主管复查，409时保留用户输入并展示资料变化，避免自动替用户确认。

这些是提供给前端协作者确认的新增接口；本次没有修改前端、运行线上验收或宣称页面已接入。规则队列不调用大模型；AI可继续给差异提示，不能指派、认定责任或审批关闭。

## 存储与限制

JSON schema升级为4，增加 `change_reviews` 集合。旧v1/v2/v3数据必须停服后在服务环境中运行 `python backend/scripts/migrate_json.py`，迁移先备份原文件，并保留账号、记忆、记录、任务编号和历史。禁止使用seed重置线上数据。启动、恢复仍拒绝未迁移或损坏文件。

本版全量扫描与JSON历史适合小规模演示，没有定时任务、容量清理、多机构隔离或完整逐老人授权。只有存在明确采用关系才能定位受影响任务，不对未记录的实际照护作影响推断。还需前端联调、Linux服务器迁移演练及真实机构验证。
